# Revisar código

> **Copia sincronizada:** la fuente es el directorio de skills de la organización (lo indica el `AGENTS.md` del repo). El Action `sync-skills` la copia a cada repo; no se edita a mano en el repo. Si una mejora nace revisando un repo, se trae primero aquí y desde aquí se propaga.

El objetivo es que **el revisor no encuentre nada que el autor pudo encontrar solo**. No es una revisión de estilo: es buscar lo que rompe, filtra o miente. Adáptala al dominio del repo con su `AGENTS.md` y su skill de datos sensibles (si la tiene).

## 1. Prepara el terreno

```sh
git fetch origin
git status --short --branch               # no mezcles cambios locales con la verificación
```

**Tu propio diff, antes de abrir el PR:** quédate en tu rama. La base es la rama a la que irá el PR (la por defecto del repo, salvo que su `AGENTS.md` diga otra):

```sh
git diff --stat origin/main...HEAD
git diff --check origin/main...HEAD      # espacios y marcadores de conflicto
```

**Un PR ya abierto (tuyo o de otra persona):** primero ponte en su HEAD y toma la base de `baseRefName`, no asumas `main`:

```sh
gh pr view <n> --json title,body,baseRefName,headRefName,isDraft,mergeStateStatus,reviewDecision,statusCheckRollup,files,commits
gh pr checkout <n>                        # ANTES de los diffs: desde la base, el diff sale vacío y "pasa"
git diff --stat origin/<base>...HEAD
git diff --check origin/<base>...HEAD
```

Cada afirmación de la revisión se ancla al **estado vivo** de git/GitHub (no a lo que recuerdas del PR) y a pruebas corridas sobre su HEAD. Si un PR desapareció de los abiertos, verifica si se mergeó o se cerró antes de opinar.

Lee **el issue enlazado completo** y la referencia que cita (plan, ADR, contrato) antes que el diff. La pregunta base: ¿el PR entrega exactamente lo que el issue pide? Si hace más o algo distinto, tiene que decirlo en la descripción.

## 2. Corre las pruebas tú mismo

Sobre el HEAD del PR, no sobre `main`. Se juzga por el **código de salida**, no por buscar palabras en el output. Los comandos exactos salen del `AGENTS.md`/`CONTRIBUTING.md` del repo; el patrón:

```sh
<build/compilador> > out.txt 2>&1; echo "exit=$?"   # p. ej. npx tsc --noEmit
<lint>             > out.txt 2>&1; echo "exit=$?"
<tests>            > out.txt 2>&1; echo "exit=$?"
```

Si el PR toca la interfaz, recorre el flujo en el navegador con datos ficticios, con cada rol que el cambio afecta (ver §6). Una prueba que nadie vio pasar **no es cobertura** — tampoco un spec que escribió un agente cuyo sandbox no pudo correrlo: la entrega no es el archivo, es la corrida.

### Dónde poner el esfuerzo — tres capas

- **Mecánica** (formato, compilador, lint, pruebas): la decide el CI **por código de salida**. Si está en rojo se arregla antes de revisar lo demás; no se "aprueba leyendo" lo que el CI debía afirmar.
- **Estructural** (aquí va tu revisión adversarial, §3): responsabilidades, errores y su registro, duplicación, valores mágicos, permisos en la capa que los impone, superficie de ataque, datos sensibles en logs y — siempre — **¿qué estado queda si el código falla a la mitad?** Dentro de una transacción, un `throw` nuevo es un rollback; una migración o provisión a medias tiene que poder correrse otra vez sin daño.
- **Narrativa** (tiene que **llegar con el PR**): ¿cumple el issue, ni menos ni "de más" sin avisar? ¿La descripción, el "cómo probar" y la documentación están al día? Si falta contexto, pídelo antes de gastar la ronda.

## 3. Caza de defectos

Recorre el diff completo con esta lista. Cada punto es un error que ya pasó en proyectos reales.

**Antes de la lista, cinco preguntas por cada función que el diff toca**, leída entera junto con sus callers y lo que llama (el revisor externo lee el repo, no el parche). En un conteo de 33 hallazgos de Greptile en 12 PRs, estas cinco explicaban 30:

- **¿Qué pasa la SEGUNDA vez?** Un reintento tras un fallo, la misma acción repetida, un seed corrido dos veces o tras un reset, otro actor que cambió el estado entre tu lectura y tu escritura. Fue la familia más grande: 11 de 33. Escribe la línea de tiempo: primera lectura → cada escritura → cada `return` temprano → qué pasa si se repite o si otro escribe en medio.
- **¿TODOS los caminos aplican la regla?** Cada caller, cada rama con `return` temprano, el servidor y no solo el navegador, cada usuario de un esquema compartido (si hay un segundo solicitante, cada campo se pregunta dos veces).
- **¿Y en los valores frontera?** Vacío, tipo genérico o ausente, el tope, un valor diminuto, el redondeo, la última vuelta de un bucle y el caso más lento que el propio repo ya anotó.
- **¿Cada prueba puede ponerse roja por SU defecto?** Quitar cada guarda, una por una, incluidas las viejas después de agregar una nueva.
- **¿Cada frase de la documentación o del comentario es cierta contra el código Y contra el resto del repo?**

1. **El hueco entre las pruebas.** No leas las pruebas buscando errores: escribe en una línea qué caso cubre cada una y busca el caso que **ninguna** cubre. Ahí está el bug. Si el arreglo es "ya no rechaza X", la prueba tiene que **partir de X ya existiendo** (la fila vieja en la base), no de alguien enviando X.
2. **Revierte el cambio y mira si algo se pone rojo.** Si quitar el arreglo deja todo en verde, nada lo sostiene: falta la prueba. Como revisor, sin tocar la rama del autor: escribe una prueba temporal fuera del repo, córrela sobre el HEAD del PR (verde) y sobre la base (roja), pega las dos salidas en la revisión y bórrala.
3. **¿La aserción puede fallar?** Una prueba que pasa con o sin el cambio, o un `if (x) expect(...)` que no corre cuando no hay `x`, no prueba nada. Lo mismo con un comando de verificación que corre sobre la referencia equivocada: un `git diff --check` lanzado desde la rama base revisa un diff vacío y sale en verde. Antes de confiar en un verde, confirma **sobre qué** corrió.
4. **Permiso por rol en la capa que corre primero.** Cada endpoint verifica sesión, **rol** y las condiciones del negocio antes de tocar datos. Ocultar un botón no es un permiso: alguien llama la API directo. Prueba cada endpoint nuevo con un rol que **no** debería poder.
5. **Datos ajenos por ID.** ¿Alguien lee o modifica un registro de otro cambiando el ID en la URL/body? ¿Un permiso sigue vigente después de revocado? Prueba el acceso cruzado.
6. **Toda entrada se valida en el SERVIDOR.** Cada `body`, `params` y `query` pasa por su validación del lado del servidor. Un aviso en pantalla no es una guarda: **`accept`, `required`, `maxLength`, `pattern`, `min`/`max` y el `disabled` de un control son pistas de UX del cliente, no guardas** — cada uno necesita su validación equivalente en el servidor, porque el cliente se salta con una petición directa. (Si una validación del servidor "no llega", no la quites: casi siempre falta el DTO/decorador, no sobra la validación.) Caso real: un `accept=".pdf"` solo filtra el selector de archivos y cualquier POST que no pase por él lo salta; se escapó porque el único filtro vivía en el HTML. La guarda fue al **core**, para que todos los callers la hereden — por cada `accept`/`required`/`maxLength`/`pattern` que proteja un dato, busca su equivalente en el servidor.
7. **Una validación nueva no debe rechazar lo legítimo que el camino hermano SÍ acepta.** Al endurecer una entrada (tipo de archivo, formato, longitud), compárala con el camino paralelo que ya funciona: un PDF real puede llegar con `Content-Type` vacío o `application/octet-stream`; un número puede venir como string. Si tu guarda nueva es más estricta que la del hermano, rechaza datos buenos. Prueba un caso **válido pero "feo"**, no solo el feliz y el malicioso. Caso real: exigir `application/pdf` rechazaba PDFs reales con tipo vacío u `octet-stream`, pero la regla del hermano (`tipo PDF || nombre .pdf`) dejaba pasar un `evil.pdf` declarado `text/html`; se escapó por copiar la **regla** del hermano en vez del **caso**. El arreglo: aceptar el nombre `.pdf` solo cuando el tipo viene vacío o genérico, y seguir exigiendo el encabezado `%PDF-`. Del hermano copia el **caso** que debe pasar, no su regla si es más floja.
8. **Quitar un valor por defecto afecta a todos los que caían ahí.** Antes de cambiar un `?? valor`, un `default:` o un `return` final, enumera quién llegaba a ese camino y qué le pasa ahora. Y mira dónde corre: dentro de una transacción, un `throw` nuevo no es un mensaje de error, es un rollback.
9. **Una lista vacía no es "no hay bug".** Los errores de filtrado (por usuario, por rol, por fecha) aparecen como listas vacías, no como errores. Prueba con datos que **sí** deberían aparecer. Un scope que devuelve vacío no demuestra que no haya bug.
10. **Todas las superficies dicen lo mismo.** Si cambia un dato o un cálculo (un total, un estado), revisa cada lugar que lo muestra: pantalla, detalle, PDF, correo, exportación, API. No pueden contradecirse sobre el mismo registro. Cuando un texto o un valor **se reemplaza**, la prueba busca también la **ausencia del viejo**: `grep` en todo el repo (código, i18n, plantillas, seeds, SQL) **y** en lo que vive en la base de datos (ajustes, CMS), y en la página verifica que el viejo ya no aparece. Una prueba que solo busca el nuevo pasa aunque el viejo siga en el pie. Caso real: la frase del inicio se cambió en el código, pero el eslogan en `site_settings` la repetía en el pie de todas las páginas; lo encontró el QA de Codex.
11. **Base de datos y datos existentes.** Todo cambio de esquema trae su migración, probada desde una base vacía **y** sobre una con datos reales de forma. Las migraciones son seguras de correr donde ya hay datos (y en todas las instancias, si el producto es multi-instancia). Las operaciones de varios pasos van en una transacción.
12. **Nada fijo de un cliente** en el código: nombres, logos, datos de contacto, catálogos y plantillas salen de la configuración, no del código.
13. **Datos sensibles del dominio.** ¿El diff recoge algo que no hace falta? ¿Lo muestra o exporta a un rol que no debería? ¿Queda en logs, mensajes de error, respuestas de la API que no lo usan o correos de más? Si el repo tiene skill de datos sensibles (p. ej. `datos-de-pacientes`, `datos-de-miembros`), córrela. **También en imágenes:** placas de vehículos, rostros, documentos, pantallas con datos. Se revisan **todas** las imágenes públicas que el PR agrega o que el sitio sirve, también las de stock o de ambientación, no solo las que el issue nombra. Ampliadas, no en miniatura. Caso real: se taparon las placas de la galería, y Codex encontró placas legibles en dos fotos de ciudades que nadie había mirado. Cualquier "sí" indebido es un `P1` que bloquea.
14. **Secretos.** Ningún token, contraseña, `.env`, clave ni firma en el diff. Las variables nuevas van en `.env.example` sin valores reales.
15. **Arreglar la capa que corre primero.** Si un bug se puede atacar en varias capas, arréglalo en la que ejecuta antes (validación/guarda), no en una posterior que tape el síntoma.
16. **Lo que pidió el aprobador gana** sobre lo "técnicamente mejor". Si el issue o el revisor pidió algo concreto, no lo "mejores" por tu cuenta dentro del PR: si crees que hay algo mejor, se discute en el issue.
17. **Interfaz.** Textos en el idioma de la interfaz del repo (en Marbust, español con tuteo). Tablas con orden, búsqueda y paginación, y con dos mensajes distintos: "no hay datos" (vacío de verdad) y "no hay resultados para tu búsqueda o filtro" (una fila dentro de la tabla). Si una búsqueda sin coincidencias deja el cuerpo en blanco, el usuario no sabe si falló la carga (caso real; lo encontró Greptile). Modales con título y botones fijos y solo el contenido con scroll. Lo que toque móvil, usable en un teléfono.
18. **Cambios en `.github/`.** Si el PR toca workflows, `.github/scripts/` o `.github/marbust.json`, revisa que no debilite ni se salte ningún check (cambiar la clase del repo para no publicar, un checker que siempre aprueba, un workflow que se edita a sí mismo). Es un `P1` aunque el check quede verde.
19. **La Novedad del PR.** La línea pública la puede leer cualquiera: si menciona una vulnerabilidad, infraestructura, un cliente o datos internos, es un `P1`. Debe describir lo que el PR hace de verdad, para el usuario.
20. **Comentarios y nombres describen lo que el código hace hoy**, no la historia de cómo se llegó. Desconfía de los absolutos ("nunca", "siempre"): busca la rama que no cumple.
21. **Un límite no se hace cumplir recortando lo que el usuario escribió.** Un `Math.min(total, 50)` o un `clamp()` dentro de un `onChange` borra en silencio lo tecleado (15 meses se vuelven 11, sin ningún mensaje). El tope se hace cumplir con un **mensaje de validación en el campo**, no recortando el valor. Revisa cada `Math.min`, `Math.max` y `clamp` dentro de un `onChange`/handler de entrada. La prueba escribe **por encima** del límite y verifica que lo escrito sigue ahí y que aparece el error. Caso real.
22. **Un redondeo o formateo no debe convertir un valor válido en cero (o en nada).** Al formatear para mostrar o imprimir, considera **todo lo que el contrato acepta**, no solo lo que hoy produce el formulario: un PDF firmado imprimía "0 years" para un valor que el prestamista recibía como positivo. Si el redondeo puede llevar un valor distinto de cero a cero, ese caso necesita su propio texto ("Menos de 1 mes"). Caso real.
23. **Un estado de la interfaz se prueba por TODAS sus salidas, no solo por la feliz.** Cuando el diff agrega un estado (menú/drawer abierto, modal, modo edición, "cargando") que además deja algo puesto (scroll bloqueado, listener, foco movido, fondo deshabilitado), haz la tabla: **cada forma de entrar y cada forma de salir**, y comprueba que lo que el estado puso se quita en **todas**. Las salidas que se olvidan:
    - **El evento que no cambia nada.** Si el cierre cuelga de un efecto (`useEffect(() => cerrar(), [pathname])`), no corre cuando el valor no cambia: tocar el enlace de la página donde ya estás deja el menú abierto. Cierra en la acción (el clic), no en la consecuencia.
    - **El entorno que cambia por debajo.** Un estado pensado para móvil sobrevive a girar la pantalla o agrandar la ventana: el menú queda "abierto" en escritorio, donde no hay ni X ni fondo para cerrarlo, y el `overflow:hidden` deja la página sin scroll. Deriva el estado efectivo (`abierto && !esEscritorio`) y haz que el bloqueo dependa de él.
    - **Lo que queda detrás.** Un overlay que tapa la página no la desactiva: con Tab se llega a los botones de atrás (incluido "Cerrar sesión"). El fondo queda `inert` mientras el overlay está abierto, el foco entra al abrir y vuelve al botón que lo abrió al cerrar. Y al revés: mover el foco por un cambio de entorno solo es correcto si el foco estaba **dentro** de lo que se oculta; si no, le robas el cursor a quien está escribiendo en un campo y gira la tablet (pasó en el mismo PR, en el arreglo del arreglo).

    - **Lo que se muestra una sola vez.** Un modal que enseña un token, una API key o un código que no se puede volver a ver **no** se cierra con Escape ni con clic en el fondo: solo con su botón ("Ya la copié"). Cerrar sin querer lo pierde para siempre. Si el modal es genérico, la opción bloquea **todas** las salidas implícitas, no solo una (caso real: se bloqueó el fondo y Escape seguía descartando la key; lo encontró Codex).

    La prueba (Playwright) recorre cada fila de la tabla y **falla al revertir el arreglo** (categoría 2). Caso real: el drawer móvil pasó la revisión con esta skill, el QA de Codex y una prueba con Playwright que solo cubría "abrir → navegar a otra página → cerrar", y Greptile encontró las tres salidas olvidadas (P1: página sin scroll tras agrandar la ventana; P2: Tab al fondo; P2: el enlace actual no cierra).
24. **¿Este `skip` (o `catch`) esconde un fallo real?** Distingue "no aplica" de "está roto": lo que no sea "no aplica" falla con su propio mensaje. Un timeout no es un diagnóstico, y un `catch` que se traga todo también se traga la señal del framework.
25. **Algo que puede fallar no decide algo que debe ser estable.** Un dato traído "si se puede" (llamada con timeout, servicio externo) metido en algo firmado, comparado, numerado o guardado como definitivo hace que el resultado dependa de la suerte. "A veces está" es peor que "nunca está".
26. **¿Qué pasa en un entorno YA desplegado?** Antes del PR: si esto llega mañana a producción, ¿qué se comporta distinto? Variables con fallback que se empiezan a exigir, claves, flags, crons y cambios de esquema (migración probada sobre datos reales, idempotente). Si hay consecuencia, va en la descripción del PR; no se espera a que el revisor la encuentre.
27. **Una prueba que solo vive en tu máquina no protege nada (regla del autor).** Si para verificar tu cambio escribiste un script (Playwright, `node`, `curl` en bucle), ese script es la prueba de regresión: va **al repo** y **al CI** (`npm test` + un paso en el workflow), con su caso rojo sin el arreglo. Si el repo no tiene framework de pruebas, sirve el runner nativo (`node --test`) sin dependencias nuevas. Una corrida pegada en el PR demuestra que hoy funciona; no impide que el próximo cambio lo rompa. El **revisor** sí puede usar una prueba temporal fuera del repo como evidencia (categoría 2): si con ella demuestra un hueco, pide al **autor** que deje la prueba en el repo; no la sube él a la rama ajena. Caso real: las pruebas de permisos por organización se corrieron solo en local y Greptile pidió subirlas; quedaron en `backend/test/` y en el CI, y 5 de 6 fallan sobre `main`.
28. **Lo que cambia el conjunto de filas reinicia lo que dependía del conjunto anterior.** Un filtro, una pestaña o un selector **fuera** del hook de la tabla cambian las filas, pero la página, la selección o el scroll siguen apuntando al conjunto viejo: estás en la página 20, filtras a 82 filas, ves la 9, y al volver a "Todos" reapareces en la 20 ("Anterior" parece trabado). El hook reinicia solo lo que conoce (búsqueda, orden, tamaño); cada control externo llama a su `resetPage()`. La prueba avanza varias páginas, cambia el filtro, vuelve y espera la página 1. Caso real: lo encontraron Codex y Greptile por separado.
29. **Una regla que se evalúa en el cliente y en el servidor usa la MISMA definición.** Si el front decide qué ofrecer (mostrar "Enviar", habilitar un botón, elegir un flujo) con su propia copia de una regla (un regex, una lista de estados, un límite), tarde o temprano difiere de la del servidor: el front ofrece algo que la API rechaza, o esconde algo que la API permite. Una sola fuente (la API devuelve el resultado, p. ej. `porCorreo: true`) o el mismo patrón en los dos lados con una prueba que compare ambos. Prueba con un caso en el borde: válido para uno e inválido para el otro. Caso real: el admin clasificaba "es correo" con un regex más laxo que la API; Codex lo encontró.
30. **"Solo una vez" se garantiza en la escritura, no en la lectura.** `if (registro.yaHecho) throw …; … save()` deja pasar dos peticiones simultáneas (otra pestaña, doble envío, reintento): las dos leen "no hecho" y las dos escriben. La guarda va en la misma operación que escribe: `UPDATE … SET hecho = ahora WHERE id = :id AND hecho IS NULL` (o una restricción única) y, si afecta 0 filas, conflicto. Deshabilitar el botón mientras se envía ayuda con el doble clic, no con la concurrencia. **Dos pruebas:** una que simula "0 filas afectadas" y espera el error, y otra que comprueba la **condición que se envía** (el `WHERE … IS NULL`) y se pone roja al quitarla. Con solo la primera, borrar la condición deja todo en verde, porque el mock devuelve 0 filas por su cuenta (lo señaló Greptile en la revisión de esta misma categoría). Y el resto del `SET` no se arma con lo leído antes: si concatena (notas, un contador), se hace en SQL sobre el valor actual (`CONCAT(notas, …)`), o una edición simultánea queda pisada (Greptile, mismo PR). Caso real: el registro manual de un seguimiento; lo encontró Codex.

31. **Un estado nuevo también sobrevive a los estados que vienen después de él.** Si el diff agrega un estado intermedio (retenido para revisión, en espera, pendiente) y enseña a otro código a reconocerlo (un reintento, un replay, una reconciliación, una pantalla), ese código lo reconoce casi siempre por **un solo valor**, y el estado tiene salidas. Lista a dónde puede pasar desde ahí y, para cada lector, pregunta si reconoce también cada estado siguiente. La prueba crea el estado, lo avanza un paso como lo haría otro actor y corre el camino que lo lee. Caso real: tras pedir cambios o cancelar una solicitud retenida, el reintento ya no la reconocía como enviada y la volvía a preparar como borrador; lo encontró Greptile.
32. **Un fixture se puede correr dos veces, y registra su limpieza ANTES de escribir.** Un seed que crea filas con un `slug` único falla la segunda vez o tras un reset parcial, y lo hace con un error que no tiene nada que ver con la prueba que lo muestra. Los ids se calculan antes de insertar (de un sufijo) y se entregan primero a la limpieza (`afterEach`); el seed los recibe, no los inventa. Si no, un insert que falla a la mitad deja huérfanas las filas anteriores. Antes de culpar a tu cambio por un `23505` (violación de unicidad), mira si es una fila que dejó otra corrida.
33. **La clave de idempotencia contiene exactamente lo que compara el servicio, y nada que cambie en cada llamada.** Abre qué compara el servicio que recibe la clave (su hash de petición): con menos campos, dos cosas distintas comparten clave y chocan (un 409 al subir dos archivos con el mismo contenido y otro nombre); con más, un reintento verdadero no se reconoce. Busca `new Date()`, `Date.now()`, `randomUUID` en todo lo que alimenta un hash, una clave o una evidencia firmada: ese valor se fija **una vez** y cada reintento lo reenvía. Revisa todos los caminos que llegan al hash, no solo el que viste. Y si lo guardas entre intentos (`sessionStorage`, `localStorage`), la llave lleva **el id de aquello a lo que pertenece**: guardado por usuario, viaja a la siguiente solicitud. Caso real: la hora del consentimiento se generaba en cada llamada y entraba en el hash, así que cada reintento era "otro" envío; el arreglo la guardó por usuario y se coló en la solicitud siguiente (Greptile, dos rondas).
34. **Un formulario con `action={...}` se resetea aunque la acción devuelva un error** (React 19, formularios no controlados). El usuario elige valores, el servidor rechaza una parte, y todo vuelve a vacío; si un campo era `required`, el siguiente envío lo bloquea el navegador sin ningún mensaje. Hacer el campo controlado no alcanza. Si el formulario puede volver con error, `onSubmit` con `preventDefault` + `startTransition(() => action(formData))`, y conserva `action={action}` para el navegador sin JavaScript. La prueba envía con un error simulado y afirma que los valores siguen ahí (en jsdom, `fireEvent.submit(form)`).
35. **Medir el layout de algo oculto da cero, y cero suele leerse como "cumplido".** Cuando un cambio esconde algo con `hidden`/`display:none` en vez de desmontarlo, busca en sus hijos cada `clientHeight`, `scrollHeight`, `getBoundingClientRect`, `IntersectionObserver` y cada "llegó al fondo / está en pantalla": `0 + 0 >= 0 - 8` es verdadero. La cura tiene dos mitades, cada una con su prueba: no medir sin altura, y volver a medir cuando aparece (`ResizeObserver`), o un contenido corto sin scroll queda trabado. Ojo con el mock: un `ResizeObserver` falso que guarda el callback en el constructor y no en `observe()` deja verde la segunda mitad aunque se quite. Caso real: un documento legal montado en un paso oculto se daba por leído antes de que el usuario llegara (Greptile, P1).
36. **Relajar un esquema compartido lo relaja para TODOS los que lo usan.** Si sacas un campo obligatorio de un esquema para un caso y lo vuelves a exigir en otra capa, busca quién usa **ese esquema**, no solo el campo que motivó el cambio. La regla nueva cubre cada uso, o el fallo llega más abajo (en un worker, después de encolar). Caso real: el esquema de dirección lo usaban titular y co-solicitante, y la verificación nueva solo miraba al titular.
37. **El chequeo y la acción que protege juzgan el MISMO objeto.** Si una verificación resuelve algo en vivo (una ruta, una configuración, un permiso) y después la acción lo vuelve a resolver y lo guarda, entre las dos lecturas puede cambiar. El chequeo va después de que se guarde lo que se va a usar, y decide con eso. Lo mismo con el estado: una guarda que lee **antes** de llamar a la función que trabaja deja una ventana, porque la función vuelve a leer por su cuenta. La que decide va sobre la fila bloqueada (`SELECT … FOR UPDATE`), en la misma transacción que escribe; la temprana solo ahorra trabajo. Y si predices lo que hará un motor de decisión (ruteo, reglas de precio) desde fuera, aplica **sus mismos filtros** (habilitado, activo, prioridad): una selección propia que cuenta un candidato que el motor descarta decide mal.
38. **Mandar una llamada a un camino más general pierde las guardas del específico.** Al cambiar el destino de una llamada (un reintento propio → el reintento general del núcleo), lista las guardas del camino viejo y las del nuevo, una por una, y pregunta qué estados llegan ahora que antes no llegaban. Lo seguro es una **lista blanca** de los estados desde los que de verdad se debe actuar. Y mira dónde se muestra el control que dispara la acción: un botón visible siempre convierte cualquier estado en una entrada posible. Caso real: un reintento derivado al camino general podía reencolar una solicitud cancelada, y con un proveedor de consulta de crédito eso es una segunda consulta en el historial de alguien que ya se retiró.
39. **Una guarda contra una carrera cubre TODAS las escrituras del camino, no solo la última.** Enumera cada escritura del camino, en orden, con sus `return` tempranos: cada una que pueda correr después de la primera lectura necesita la misma pregunta sobre su propia fila bloqueada. Si tu propio comentario nombra una escritura previa al bloqueo, ese comentario es el hallazgo. Y una guarda nueva más arriba puede volver decorativa la prueba de una guarda de más abajo (sigue verde, pero ahora la frena la nueva): al agregar una guarda, quita **cada una de las anteriores** y mira su rojo, y la prueba de cada guarda construye el caso donde **solo ella** puede frenar. Con una base simulada, el mock no ejecuta un `WHERE` condicional: probar que la escritura se frena no demuestra nada, pero sí se comprueba que la consulta enviada **incluye** la condición (como en la 30), y esa prueba se pone roja al quitarla. Un `SELECT … FOR UPDATE` con la revisión explícita en el código se puede probar además por su efecto.
40. **Una espera nueva hereda un timeout: ¿cubre el caso más lento que el repo ya anotó?** Al agregar un `waitForResponse`, `waitFor`, `expect.poll` o un `fetch` con abort, pregunta de qué valor hereda y lee los comentarios de ese config: si el repo documenta un caso más lento, la espera lo cubre explícitamente. Si la espera nueva va antes de otra que ya existía, no puede ser más corta que la vieja, o cambia el límite del flujo entero sin que el diff lo diga. Caso real: una espera de 30 s heredada delante de una de 90 s, en un config que anotaba un login de 31,8 s (Greptile, P1).
41. **La última vuelta de un bucle de reintentos.** ¿La espera, el log o el efecto de "voy a reintentar" corre también cuando ya no habrá otro intento? La condición de salida va **antes** de la espera. El último valor de un contador es un valor frontera.
42. **Cuatro que el checklist general de Greptile pide.** Rendimiento: ¿agregaste una lectura a la base por cada llamada o por cada fila (consulta dentro de un bucle, segunda lectura del mismo registro)? Si es a propósito, dilo en el PR. Registro: un rechazo nuevo ¿deja rastro en el log del servidor, o solo llega a la pantalla? Valores mágicos: una lista de estados, un tope o un plazo escrito como literal en dos sitios es el próximo desfase; una constante con nombre y un solo dueño. Bandera: un cambio de conducta que no se puede revertir sin desplegar, ¿necesita interruptor? Si no lo lleva, la razón va en la descripción del PR.
43. **Después de una escritura condicionada, nada vuelve a guardar la entidad leída antes.** Un `UPDATE … WHERE version = :vista` seguido de `repo.save(entidad)` con la entidad que se leyó al principio deshace lo que la guarda protegía: si otro escribió en medio (una línea agregada, un estado cambiado), el `save` lo pisa con la copia vieja. Una sola escritura con **solo** los campos pedidos, la condición en el mismo `WHERE`, y se relee al final para responder. Busca en el diff cada `save(` posterior a un `update(`/`execute()` condicionado sobre la misma fila. La prueba hace que otro escriba justo antes de la escritura y comprueba que lo suyo sigue ahí, y que no hay ningún `save` de la entidad completa. Caso real (Greptile, P1).
44. **Una comparación en SQL usa la collation de la columna, no la de tu cabeza.** Con una collation que no distingue mayúsculas ni acentos (lo normal en MySQL/MariaDB, `*_ci`), `WHERE notas = :previas` da "Remoto" = "remoto": un control de versión deja pasar el cambio de otro como si nada hubiera cambiado. Con `PAD SPACE`, `= ''` también da por vacía una cadena de solo espacios. En una comparación que decide un conflicto o una igualdad exacta, `BINARY col = BINARY :valor`, y `CHAR_LENGTH(col) = 0` en vez de `= ''`. Una collation `_bin` **no alcanza**: `utf8mb4_bin` también es `PAD SPACE`, así que `'nota' = 'nota '` sigue dando verdadero y el espacio final que agregó otro se pisa. Solo sirve una collation `NO PAD` (p. ej. `utf8mb4_0900_bin` en MySQL 8), comprobada en `information_schema.COLLATIONS.PAD_ATTRIBUTE` del motor de producción. La prueba usa un valor que solo difiere en mayúsculas y otro que solo difiere en un espacio final, y la comprobación se corre una vez en el motor real: un mock en JavaScript compara exacto y no ve el hueco. Caso real (Greptile, P1; confirmado en MariaDB).
45. **"0 filas afectadas" no es éxito si la petición traía más de lo que se comparó.** Un atajo que dice "la condición falló, pero la base ya tiene el valor pedido, así que está bien" solo vale para ese campo. Si la petición traía otros (un estado, una fecha), esos no se escribieron, y responder éxito (y anunciar el cambio) los descarta en silencio. O se responde conflicto, o se aplican aparte los demás campos, o se comprueba que **todos** ya coinciden. La prueba manda el campo comparado ya igual **más** otro campo distinto, y afirma según la conducta elegida: o conflicto **sin ningún cambio guardado**, o éxito con **todos** los campos pedidos guardados. Lo que nunca pasa es éxito con un campo sin escribir. Caso real (Greptile, P1).
46. **Una reserva no prueba que el efecto externo ocurrió.** Para "solo una vez" sobre algo que sale del sistema (correo, cobro, llamada a un proveedor), la secuencia es reservar → hacer → confirmar, y cada paso tiene su estado. Si la reserva se marca con el mismo valor que "hecho" (`fechaEnvio` puesta antes de enviar), un fallo o una caída entre medio deja algo que no ocurrió marcado como ocurrido, y la guarda bloquea el reintento para siempre. Revisa cada salida: **falla** → se libera solo la reserva propia (condición con su valor exacto), sin pisar un estado que otro cambió en medio; **el proceso cae** → la reserva vence y se puede recuperar; **incierto** (el efecto salió pero la confirmación no se escribió) → no es lo mismo que fallar: antes de repetirlo se consulta un registro del efecto o se pide confirmación explícita, o el destinatario lo recibe dos veces. Una prueba por cada salida, y cada una roja al quitar su guarda. Caso real (Greptile, P1, tres rondas).
47. **El registro que dice "ya ocurrió" se liga a la entidad y al intento, no se busca por contenido.** Buscar en un log por destinatario + asunto + fecha confunde dos entidades que producen el mismo contenido (dos registros al mismo correo y el mismo puesto) y dos intentos de la misma entidad. El efecto se registra con una referencia propia (`<origen>:<id>:<intento>`, con el intento fijado en la reserva) y la consulta busca exactamente esa referencia. La prueba siembra en el registro el efecto de **otra** entidad con el mismo contenido, y otro de un intento anterior, y afirma que ninguno cuenta. Un mock que devuelve "encontrado" por su cuenta no prueba la consulta: el registro simulado evalúa el `where` contra filas guardadas. Caso real (Greptile, P1).
48. **Tras el veredicto del servidor, la UI se pone al día en todo lo que muestra.** Un 409 no es "algo falló": trae una decisión (ya estaba hecho, falta confirmar, alguien cambió el dato). El aviso específico de conflicto sale **solo** con ese código; un error de red o un 500 lleva un mensaje general, o se le pide al usuario descartar su trabajo cuando reintentar bastaba. Y se invalidan **todas** las consultas que alimentan los controles visibles (la lista **y** la vista previa o el detalle del modal), se limpia el estado local que dependía de la versión vieja (una casilla marcada, el error de la mutación al reabrir), y al reabrir el editor se cargan los datos actuales, no la copia en caché. La prueba (Playwright con la API simulada) responde 409 y afirma que los controles cambiaron sin cerrar el modal; se pone roja al quitar la invalidación. Caso real (Greptile, P1 y P2, dos rondas).

49. **Revisar un PORT o reimplementación: compara contra la FUENTE, no solo contra el contrato.** Cuando el código reimplementa una versión que ya funciona (portar un módulo de un install viejo, reescribir un servicio), el mayor riesgo es perder **en silencio** protecciones que la fuente sí tenía. Haz el diff del comportamiento nuevo contra el de la fuente y lista cada guarda/conducta que tenía: fuerza de la validación, rate-limit, actualización de flags de estado, límites de tamaño/truncado, registro de errores, reintentos. El port las preserva, o el PR dice por qué las deja ir. Revisar solo contra el **consumidor** (el contrato del frontend: mismas rutas y respuestas) no ve nada de lo que la fuente hacía **detrás** de ese contrato. Caso real: un backend público portado de un install viejo pasó el QA contra el contrato del frontend, pero Greptile encontró que había perdido el score de reCAPTCHA v3, el rate-limit por IP, el `UPDATE … SET emailed = 1`, el producto en el aviso y el truncado del mensaje — todo lo tenía la fuente (6 hallazgos en un PR).
50. **Una guarda de seguridad que se desactiva sola cuando falta o no se puede leer su configuración es una vuln, no un default seguro.** Cuando un control (captcha, firma, autenticación) depende de un secreto/config guardado, y el código **salta** el control si ese secreto está ausente **o** no se puede leer (no descifra, la llave se rotó o se perdió), un atacante se beneficia de una config rota. Distingue "no configurado a propósito" (la fila no existe) de "configurado pero ilegible" (la fila existe pero no descifra): el segundo **rechaza**, no salta. Un lector que devuelve `null` en ambos casos borra esa distinción. Caso real: `publicSecret()` devolvía `null` tanto si el secreto no estaba como si no descifraba con la llave, y la ruta pública saltaba el reCAPTCHA en ambos → perder o rotar la llave desactivaba el captcha sin avisar (Greptile, P1).
51. **Una notificación externa respeta el límite del proveedor, lleva lo que el operador necesita, registra su resultado y no bloquea la respuesta.** Para cada envío a un canal externo (Telegram, email, push): (a) el contenido puede pasar el **límite de tamaño** del proveedor (Telegram `sendMessage` = 4096) → se trunca o se parte, o el aviso se pierde en silencio; (b) el aviso incluye el **dato clave de la acción** (el producto/pedido, no solo en el asunto del correo que el otro canal no recibe); (c) el **resultado se registra**: un flag de "enviado" (`emailed`) se actualiza al tener éxito y un fallo se loguea con el id — un "best-effort" que descarta el resultado deja al operador sin aviso y a la UI mintiendo `enviado: false`; (d) los envíos **no bloquean** la respuesta al usuario más de lo razonable: cada uno con timeout corto y en try/catch, y si pueden ser lentos o muchos (un envío por operador), el `201` no espera a todos. Caso real: un mensaje de hasta 5000 chars se mandaba entero a Telegram (se perdía > 4096), el producto solo iba en el asunto del email, `leads.emailed` nunca se actualizaba, y el `201` esperaba un envío secuencial por operador con timeout de 6 s (Greptile, P2 ×4).
52. **Todo endpoint de escritura PÚBLICO (sin sesión) lleva rate-limit del lado del servidor.** Un formulario público (contacto, lead, registro, reset) sin límite deja que cualquiera inserte filas y dispare correos/avisos en bucle, aunque mande tokens válidos. El límite va en el **servidor**, **antes** de la verificación cara y de la escritura (p. ej. N por IP en M minutos → `429`), no en el cliente. Si el contrato documenta un `429` que el código no implementa, ese hueco es el hallazgo. Caso real: la ruta pública de leads no tenía ningún contador y aceptaba envíos repetidos indefinidamente (Greptile, P1/P2 de seguridad).

53. **Un upsert por un id (o clave) que cada sistema asigna por su cuenta puede pisar una fila DISTINTA.** Una migración o importación que hace `ON DUPLICATE KEY UPDATE` (o borra y reinserta) usando un id traído del origen asume que un id igual = la misma entidad. Cuando origen y destino asignan ids de forma independiente (dos instalaciones, dos BD), un id que coincide **no** prueba que sea el mismo registro: el upsert pisa los datos y el estado de otra persona. Lo seguro: validar en seco **todas** las colisiones de unicidad del destino (por recurso) y **abortar** si el destino ya tiene filas que chocan (pensar la importación para un destino fresco), e `INSERT` sin upsert ni borrados "de barrido" (no borrar las imágenes/hijos de una fila que creés tuya). Caso real: una migración de leads hacía `ON DUPLICATE KEY UPDATE` por id y borraba todas las imágenes del producto; como ambas BD asignan ids solas, podía reemplazar el prospecto y el seguimiento de otra persona (Greptile, P1).
54. **Una lista de placeholders o un `IN (…)` armado desde datos sin acotar se rompe en el tope del motor.** Meter "todos los ids/slugs" en un solo prepared statement (`WHERE id IN (?, ?, …)`) falla cuando la lista supera el límite del motor (MySQL: 65 535 placeholders) — y falla **antes** de hacer nada, aunque cada fila fuera válida. Partir en lotes acotados (p. ej. 1000) y unir resultados. Vale para cualquier consulta cuyo número de parámetros dependa del tamaño de la entrada. Caso real: la validación del destino metía todos los ids de leads en un `IN` y a gran volumen rechazaba el import entero (Greptile, P2).
55. **Un control de seguridad donde el CLIENTE provee el valor con el que se compara se anula solo.** Si una verificación compara algo del servidor contra un valor **que el mismo cliente manda** (la `action` esperada de un captcha, el rol pretendido, el precio "esperado", el estado contra el que se valida), el atacante elige las dos puntas y el control no filtra nada. El valor con el que se compara lo fija el **servidor** desde su propio contexto validado, nunca el request. Y una verificación v3 exige los campos que una respuesta legítima siempre trae (score **y** action): aceptar `success` a secas deja pasar respuestas incompletas. Caso real: el reCAPTCHA tomaba la `action` esperada de `body['recaptchaAction']`, así que un bot mandaba un token y la action que ese token declaraba y pasaba; el arreglo derivó la action del contexto del servidor (hay producto → interés, si no → contacto) y exigió el score (Greptile, bloqueaba el merge). **Ojo con el falso arreglo:** "derivar del servidor" no es derivar de **otro campo del request** que parezca contextual — si la action esperada sale de `!empty($body['product'])`, el cliente sigue eligiéndola (manda o no `product` y genera el token con esa action). El valor fijo va atado a la **ruta/endpoint** del servidor (una constante por ruta), independiente de cualquier campo del cuerpo.

56. **Deduplicar o comparar valores con `SORT_REGULAR` (o `==`) colapsa cosas DISTINTAS que se ven numéricas.** Un `array_unique($valores, SORT_REGULAR)`, un `in_array($x, $lista)` sin `true`, o cualquier comparación laxa tratan `'1'` y `'01'`, o `'1e2'` y `'100'`, como iguales (numéricos equivalentes con distinta forma textual). Si eso alimenta una comprobación (de colisiones, de pertenencia, de ya-visto), **deja de revisar algunos valores** y los pierde en silencio: el chequeo "pasa" y el problema aparece después (un `UNIQUE` que revienta en la escritura real). Deduplicá y compará **como texto** (`SORT_STRING`, `array_unique(..., SORT_STRING)`, `in_array(..., true)`, claves de array que son strings). La prueba usa dos valores que solo difieren como número vs texto (`'1'` y `'01'`) y espera que **los dos** se consideren. Caso real: la validación en seco de una migración deduplicaba slugs con `SORT_REGULAR` y se saltaba colisiones de slugs numéricos distintos (Greptile, P2).
57. **Un cliente asume UNA sola forma de respuesta cuando el endpoint devuelve VARIAS.** Si una ruta responde con formas distintas según el estado del flujo (p. ej. `{ token, usuario }` cuando inicia sesión, pero `{ message }` cuando solo activa/confirma algo), el cliente que trata **toda** respuesta como la que trae datos guarda una sesión o un estado roto con `undefined` y sigue como si todo hubiera salido bien. Enumera **cada** forma que la ruta puede devolver y maneja cada una por separado (`if ('token' in data && data.token) …` antes de usar `data.token`; si no, mostrar el mensaje, no navegar). Nunca asumas la forma feliz. La prueba manda cada forma y verifica que la que **no** trae datos no crea sesión/estado. Caso real: un `verify-otp` devolvía `{ token }` al iniciar sesión o `{ message }` al activar una cuenta pendiente; el front trataba todo como login, hacía `setSession(undefined)` y navegaba con una sesión rota al meter ahí un código de activación.

58. **Un valor que una capa YA compuso y después se GUARDA tal cual se vuelve a componer al leerlo (doble prefijo).** Si un endpoint de subida/creación devuelve una forma ya compuesta (una URL con prefijo, un path absoluto, un slug con su ruta) y esa forma se **guarda tal cual**, el presentador que la lee y la vuelve a componer produce `/uploads/uploads/…` (o `/catalog/catalog/…`): una ruta que ya no existe y responde 404, en silencio. Define UNA forma canónica en la base (la cruda, sin prefijo) y: o **normalizás al guardar** (quitás el prefijo antes del INSERT), o no re-componés al leer — nunca las dos. Caso real: el endpoint de subida de fotos devolvía `/uploads/<path>`, el guardado lo almacenaba así, y el presentador volvía a prefijar `/uploads/` → `/uploads/uploads/…` 404 (Greptile, P1).

59. **Una respuesta condicional (304/ETag/precondición "ya hecho") debe confirmar que el recurso EXISTE antes de darla.** Comparar `If-None-Match`/ETag —o cualquier "no modificado / ya estaba" — **antes** de verificar que el recurso existe devuelve 304 + caché larga para algo ausente o borrado, y el cliente sigue mostrando una copia vieja de una imagen que ya no está. La precondición aplica **solo** a un recurso que existe: verificá existencia primero, y recién ahí compará la precondición. Caso real: un handler de imágenes comparaba `If-None-Match` antes de confirmar la fila; una petición con el ETag (determinístico por la ruta) de una imagen borrada recibía 304 y un año de caché (Greptile, P2).

60. **Validá tamaño Y dimensiones ANTES de cargar/decodificar una entrada no confiable en memoria.** Decodificar una imagen (o parsear un documento) antes de acotar sus bytes y sus dimensiones agota la memoria aunque el archivo comprimido sea chico (bomba de descompresión: 1 KB → millones de píxeles). El tope de bytes de entrada **y** el de dimensiones/píxeles van **antes** de `imagecreatefromstring`/el parser, no después de redimensionar. Verificar el tamaño de la **salida** no acota la memoria que costó **abrir** la entrada. Caso real: un upload redimensionaba a 1200 px y medía la salida, pero abría el original completo primero — un archivo chico con dimensiones enormes agotaba la memoria de la petición (Greptile, P2).

61. **Verificá que una capacidad opcional existe antes de usarla, y validá la SALIDA de una conversión.** Antes de llamar una función de una extensión opcional (`imagewebp`, un códec/driver que puede no estar), chequeá `function_exists`/disponibilidad — llamarla cuando no está es un fatal, no un respaldo elegante. Y validá lo que la conversión **produjo**: no asumas que generó algo válido (una cadena vacía puede "cumplir" un límite de tamaño máximo y pasar). Caso real: una ruta usaba `imagewebp` tras chequear solo `imagecreatefromstring`; con GD que abre pero no escribe WebP, fallaba antes del respaldo, y una salida vacía pasaba el límite de tamaño (Greptile, P2).

62. **Una prueba puede pasar por la razón EQUIVOCADA: la excepción/el error que afirma viene de otra causa, no de la que se prueba.** Una prueba que espera "lanza `X`" pasa igual si **otra** cosa de ese camino lanza el mismo tipo (p. ej. pasar una dependencia nula hace que una conexión inválida lance la misma `InvalidArgumentException` que la validación que querías probar). Así la prueba sigue verde aunque la validación se rompa. Aislá: ejercitá **solo** la función bajo prueba (llamá a la validación directo, sin forzar un fallo colateral), y agregá un caso **válido que NO lance** — si la validación distingue, el válido pasa y el inválido falla. Caso real: dos pruebas de "rechaza no-WebP / >1 MB" llamaban al `store` con un PDO nulo, que también lanzaba `InvalidArgumentException` por la conexión → pasaban aunque la validación de formato dejara de rechazar (Greptile, P2).

63. **Una decisión de autorización basada en un claim del JWT (rol, nivel, permisos) que puede cambiar en el servidor queda stale.** Si un guard decide por `req.user.nivel`/`roleId`/un permiso que viene del token, y ese dato cambia en la BD (degradar un rol, quitar un permiso) sin revocar los tokens ni refrescarlos, un token viejo con cuenta aún activa sigue pasando con el privilegio viejo. El guard que protege una acción sensible consulta el **rol/permiso ACTUAL en la BD** (por el id del usuario del token), no el claim del JWT. **Distinto de la cat. 4** (que exige validar el rol en el servidor): aquí el punto es que el rol/permiso que se valida debe ser el **vigente en la BD**, no el claim del token, que no se refresca al cambiar; y de la cat. 5 (permiso revocado): aquí es un cambio de rol/privilegio, no una revocación puntual. La prueba: token con nivel alto en el payload + cuenta cuyo rol en la BD ya bajó → 403, y se pone roja si el guard vuelve a leer del claim. Caso real: un ex-SuperAdmin degradado conservaba el nivel en su JWT y podía crear API keys permanentes para otro usuario; el guard miraba el claim, no el rol real. Es lo mismo que re-chequear que la cuenta siga activa en el guard, pero para el rol/permisos.
64. **Un rate-limit o un log por IP detrás de un reverse proxy agrupa a todos / registra la IP equivocada si no se configura el trust-proxy.** Cuando la app corre detrás de Apache/Nginx (socket unix o proxy), `req.ip`/`@Ip()` devuelve la IP del proxy (o una sola para todos), no la del cliente real, salvo que se configure el proxy confiable (`trust proxy`) y se lea la cabecera reenviada. Un rate-limit por esa IP mete a todos en el mismo bucket (un cliente bloquea a los demás) y el log guarda la IP equivocada. Dos partes: (a) configurar el trust-proxy **con el número correcto de saltos / las IPs del proxy confiables**, y que el proxy **sobrescriba o limpie** el `X-Forwarded-For` que manda el cliente — un trust-proxy flojo (p. ej. `true`/confiar en todo) o un proxy que no limpia esa cabecera deja que el cliente **falsifique** su IP, evada el rate-limit y contamine los logs; (b) para un límite por actor usar una clave **estable** (la API key, el usuario, la sesión), no solo la IP. Caso real: el throttle de un login por API key usaba `@Ip()` sin trust-proxy; en prod (tras Apache por socket) todos caían en el mismo contador y la IP guardada era inútil.
### Pase de impacto en TODO el repo (no solo el diff)

El bug que llega a producción casi siempre vive en un **consumidor que el diff no muestra**. Para cada cosa que cambió, enumera quién la usa en todo el repo (y en el repo hermano, si el producto tiene back y front separados) y verifica que ninguno se rompe:

- **Función o export** (firma, retorno, un default, un `?` quitado, un valor nuevo en un enum): busca cada llamada.
- **Tabla o columna**: services, consultas, DTOs, seeds, migraciones y los tipos del front. Quitar o renombrar rompe lecturas; una columna nueva obligatoria rompe inserciones existentes.
- **Ruta, DTO o forma de la respuesta**: cada cliente que la llama o la interpreta.
- **Variable de entorno, flag o clave**: dónde se lee y en qué entorno nunca se configuró.

Si no puedes nombrar a los consumidores de lo que cambió, todavía no revisaste el cambio: leíste el diff.

Antes de reportar un hallazgo, **verifícalo contra la línea**. Un hallazgo equivocado cuesta una ronda de revisión. (Un proyecto con un revisor de exigencias propias puede tener su skill específica, que complementa a esta; sus lecciones generales se traen aquí.)

> **Que un agente de QA (Codex u otro) lea o corra esta skill no reemplaza tu propio pase.** Antes de abrir cada PR, carga la skill y recorre **todas** sus categorías sobre el diff completo, aunque el PR ya esté autorizado.

## 4. Formato del resultado

Como el de Greptile: que cualquiera (o una IA) pueda ir directo a la línea y corregir. Empieza con la **puntuación** y el conteo, y después cada hallazgo:

````markdown
**Puntuación: 3/5** · 1 P1 · 1 P2 · 0 P3

### P1 — GET /records/:id deja leer registros ajenos
`src/records/records.controller.ts:24-31`

Solo verifica la sesión. Un usuario con sesión lee el registro de otro cambiando el ID en la URL,
porque el endpoint no comprueba que el registro sea suyo.

<details><summary>Prompt para corregir con IA</summary>

```text
Archivo: src/records/records.controller.ts, líneas 24-31.
Problema: GET /records/:id solo verifica la sesión; no valida que el registro pertenezca al usuario.
Corrige: antes de leer, comprueba que record.ownerId === usuario.id (o que el rol lo permita) en el endpoint.
Hecho cuando: una prueba que pide el registro de otro usuario espera 403, y se pone roja si quitas la comprobación.
```
</details>
````

- **`P1`**: rompe algo, pierde o pisa datos, expone datos o contradice el issue. **Bloquea el merge.**
- **`P2`**: defecto real que no rompe hoy (accesibilidad, un caso borde, la prueba de regresión del comportamiento que cambió). **También se corrige antes del merge.**
- **`P3`**: estilo o legibilidad. Se corrige o se responde con su justificación; un P3 **respondido** no baja la puntuación.
- **Puntuación:** `5/5` sin P1 ni P2 abiertos y con cada P3 corregido o respondido; `4/5` si solo quedan P2; `3/5` o menos con algún P1 (cuantos más, más baja).
- **El prompt es autocontenido:** archivo y líneas, el problema, cómo corregirlo y el **"hecho cuando"** (la prueba que se pone roja sin el arreglo). Quien lo pegue en otra sesión no debe necesitar leer la revisión entera.

**En un PR**, cada hallazgo va como **comentario en su línea** dentro de una sola revisión, y el resumen con la puntuación va en el cuerpo:

```sh
# revision.json: {"event":"REQUEST_CHANGES","body":"**Puntuación: 3/5** …",
#   "comments":[{"path":"src/records/records.controller.ts","line":31,"start_line":24,"start_side":"RIGHT","side":"RIGHT","body":"### P1 — …"}]}
gh api repos/OWNER/REPO/pulls/48/reviews --input revision.json
```

**Hallazgos fuera del diff** (un consumidor sin cambios, un repo hermano, del pase de impacto): GitHub no deja comentarlos en su línea. Van en el **cuerpo** de la misma revisión, con su `archivo:líneas` y su prompt, o anclados en la línea del diff que los provoca.

Termina con lo que **no** pudiste verificar y por qué. Si no hay hallazgos, dilo directo (**5/5**) y nombra el riesgo que queda.

Al contestar una re-revisión: una disposición por hallazgo (`CORREGIDO` con su commit, o `NO APLICA` con el `archivo:línea` que lo demuestra), los hallazgos nuevos aparte y, al final, **una línea** con lo que falta exactamente para llegar a 5/5.

## 5. Después de la revisión

- **Autor:** responde cada hallazgo con `CORREGIDO` (y el commit) o con la evidencia `archivo:línea` de por qué no aplica. Nada de "tienes razón" sin cambio.
- **Revisor (QA):** publica el resultado como **revisión de GitHub con la cuenta revisora** del repo: una **cuenta de usuario** con permiso en el repo, distinta de la que abrió el PR, que indican su `AGENTS.md` o `CONTRIBUTING.md`. **Si ninguno de los dos la nombra**, se usa una **cuenta de usuario autorizada por el dueño del repo** &mdash;en una organización, una cuenta miembro con permiso (nunca la organización en sí: una org no inicia sesión ni publica revisiones); en un repo personal, otra cuenta tuya&mdash;, siempre distinta del autor. **El autor** la deja anotada en el `AGENTS.md` **en su rama, antes de pedir la revisión** (o se tramita en otro PR aparte); el revisor no toca la rama del autor. Si no tienes acceso a una segunda cuenta de usuario, dilo en el PR en vez de aprobar con la del autor. (Con `gh` y varias cuentas: `GH_TOKEN=$(gh auth token --user <cuenta-revisora>) gh …`.) No como comentario suelto, y con los hallazgos en sus líneas (§4). *Request changes* si queda algún P1 o P2; *Approve* solo con **5/5**. Al aprobar, di en una línea qué verificaste y cómo.
- **Después de «Listo para revisar»:** vuelve a correr las pruebas sobre el nuevo HEAD, revisa cada respuesta (`CORREGIDO` con su commit, o la evidencia) y publica otra revisión: *Request changes* si queda algo, *Approve* solo con **5/5**. Un commit después del *Approve* lo invalida.
- **Itera hasta limpio, máximo 3 vueltas.** El arreglo introduce bugs: en cada vuelta revisa el diff **nuevo completo** (no solo el punto que señalaste), vuelve a correr las pruebas sobre el nuevo HEAD y repite el pase de impacto sobre lo que cambió. Si a la tercera vuelta siguen apareciendo bloqueantes, el PR está mal planteado: divídelo o cambia el enfoque.
- **Confianza honesta antes de aprobar**, en tres líneas: qué verificaste y cómo, qué quedó sin verificar y por qué, y qué se comporta distinto en producción al desplegarlo. Si no puedes responderlas, no apruebes por inercia.
- **Checks en verde por código de salida.** No se aprueba con un check en rojo. Si falla por la plantilla o el título del PR, se corrige el PR y se espera el re-run; no se mergea por encima.

### Quién revisa

**Dos cuentas:** una desarrolla (rama, commits, PR) y otra revisa (revisión y aprobación). El autor no se aprueba a sí mismo. Quién hace la revisión, en este orden:

1. **Una herramienta externa de revisión**, si el repo la tiene (Greptile u otra). Su revisión da la puntuación que manda para el merge. Tu pase y el de otra IA van **antes**, en local, para que la herramienta (con créditos limitados) solo vea un PR ya limpio.
2. Si no hay herramienta, **otra IA distinta de la que escribió el código**: si escribió una, revisa la otra. Otro modelo trae otro contexto y ve lo que el autor da por supuesto. Corre esta skill y publica con la cuenta revisora.
3. **Nunca la misma sesión que escribió el código.**

### Revisor externo (Greptile u otro bot)

Cuando el repo tiene un revisor automático como Greptile, es una capa **más**, no un reemplazo de tu pase ni del QA de Codex:

1. Pídele la revisión **después** de que tu pase y el de otra IA estén limpios, en local: así sus créditos (limitados) se gastan en lo que nosotros no vimos. Una etiqueta por vuelta, con todo lo de esa vuelta ya corregido.
2. Si no revisa solo, etiquétalo con un comentario: `@greptileai review`. **No re-revisa al actualizar la rama:** después de cada push de correcciones hay que volver a etiquetarlo, una vez por vuelta.
3. Cada hallazgo se trata como el de cualquier revisor: verifícalo contra la línea, corrígelo con su prueba de regresión (roja al revertir) y contesta su hilo con `CORREGIDO` + commit, o con la evidencia de por qué no aplica.
4. **Cada hallazgo que esta skill no habría atrapado se convierte en una categoría nueva aquí**, con su caso real (sin nombrar el proyecto), por PR al repositorio fuente de skills. Así el siguiente autor lo encuentra solo.
5. **Se mergea solo con 5/5 sobre el último commit**, dado por quien revisa según *Quién revisa*: la herramienta externa si el repo la tiene, o si no la otra IA. Un 4/5 o un hallazgo "no bloqueante" se corrige igual: menos de 5/5 es un PR sin terminar. Si un PR **ya mergeado** recibe menos de 5/5 (p. ej. la herramienta se instaló después), se abre un issue y un PR de arreglo hasta 5/5. Caso real: un PR se mergeó con el QA de otra IA limpio y antes de tener la herramienta; al revisarlo después le dio 3/5, con dos P1 que borraban datos.

## 6. Smoke de UI — solo evidencia real

Si el PR toca la interfaz:

1. Usa el navegador que la sesión tenga de verdad (Playwright, por ejemplo). Si no hay, dilo; no improvises.
2. Prefiere la preview del PR si existe. Si pide login, **no saltes la autenticación ni falsees capturas**. Si no hay preview, levanta el entorno local solo si es seguro (sin apuntar a producción). Las credenciales de prueba **nunca** se escriben en el PR ni en una skill: salen de donde el `AGENTS.md` del repo diga.
3. Evidencia **solo real**: capturas del entorno de verdad, nunca mockups ni imágenes sintéticas.
4. Mide, no mires: ancho de página contra viewport (sin scroll horizontal) a 390 px, en tablet (768–1440) y en escritorio; el estilo calculado cuando sospeches que el CSS no cargó. Prueba los estados de la categoría 23 (abrir, cerrar por cada salida y redimensionar).

## 7. Listo para merge — y el freno antes de producción

Antes de decir "listo para merge": el PR no es borrador y es mergeable (o el `mergeStateStatus` está entendido), los checks requeridos están en verde, la verificación corrió sobre el HEAD del PR, el smoke de UI está documentado si cambió la interfaz, y las implicaciones de migración, configuración o despliegue están en la descripción.

- **5/5 o no se mergea.** La revisión propia, la de otra IA y la de la herramienta externa (si el repo la tiene) cierran en 5/5 sobre el último commit: todo P1 y P2 corregido o respondido `NO APLICA` con evidencia.
- **Preparar un PR no autoriza el merge. Mergear no autoriza el despliegue.** En un repo con auto-deploy, mergear **es** desplegar: el merge a la rama de producción solo va con el OK explícito del responsable de producción que indique el repo para ese cambio.
- La aprobación la da la cuenta revisora (la empresa), nunca el autor.
- **Squash-merge con cuerpo completo.** El título del commit es el del PR y el **cuerpo resume todo lo que se hizo**, en lista: quien lee el historial no debe adivinar ni ir a leer el issue. El cuerpo por defecto de GitHub (los "wip", "arreglo" de cada commit) no sirve: se reescribe.

    ```sh
    # ejemplo: PR 48 que cierra el issue 45 — cambia los números por los tuyos
    gh pr merge 48 --squash --subject "fix(layout): menú lateral como drawer en móvil (#48)" --body "$(cat <<'EOF'
    - qué cambió en el backend (endpoints, reglas)
    - qué cambió en la interfaz
    - pruebas y verificación

    Closes #45
    EOF
    )"
    ```
- Después del despliegue: confirma la versión que quedó viva (el commit desplegado de verdad, no el "success" del pipeline, que solo confirma el disparo), haz smoke de las rutas cambiadas en producción y cierra con evidencia: commit, despliegue, resultado del smoke y salvedades. Los comandos de despliegue salen del `AGENTS.md` del repo.
